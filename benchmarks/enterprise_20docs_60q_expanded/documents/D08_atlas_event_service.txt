Atlas 事件服务是集团内部的事件分发基础服务，用于在文档、索引和其他业务状态发生变化时向订阅系统发送事件。它的核心职责是事件接收、主题组织、订阅管理和消费状态维护，而不是承担 HTTP API 网关、知识检索或用户认证。Atlas 会被多个上层系统使用，因此需要特别区分“谁依赖 Atlas”和“谁负责 Atlas”这两种不同关系。

赵启负责 Atlas 事件服务。赵启同时是应用架构部负责人，这使 Atlas 的服务治理与集团共享架构工作保持一致。赵启负责 Atlas 并不意味着他负责所有消费 Atlas 事件的项目。例如北极星检索平台使用 Atlas 的文档变更事件，但北极星自身有独立负责人。知识库在负责人关系上以显式 RESPONSIBLE_FOR 为准，不根据上下游依赖自动扩展。

Atlas 使用 Kafka 作为消息队列，负责承载事件主题与消费流程；同时使用 PostgreSQL 保存事件订阅配置、消费位点等元数据。Kafka 解决消息流转问题，PostgreSQL 则用于保存需要结构化管理的服务状态信息。这两个技术角色不同，不能把 PostgreSQL 描述成消息队列，也不能把 Kafka 描述成权限策略数据库。服务技术选型以当前文档记录为准。

Atlas 向北极星检索平台提供文档变更事件。北极星消费事件后更新检索索引，这一链路帮助知识库中的新版本更快进入检索流程。Atlas 与云桥 API 网关虽然都属于共享服务，但职责不同：云桥处理 HTTP 接入和路由，Atlas 处理事件分发。Atlas 也不是猎户座权限服务，后者承担统一鉴权。

陈航不是 Atlas 的负责人；陈航负责的是北极星检索平台。该明确区分用于防止把“消费某服务”错误解释成“负责某服务”。本文件没有提供 Atlas 的 SLA 可用性百分比，也没有给出可以据此计算 SLA 的运营数据，因此相关问题应回答资料未提供，而不能凭企业服务常见目标进行猜测。

事件服务的运维材料可能同时提到消费者、生产者、消息主题和数据库状态，但这些内容只说明事件链路，不自动建立项目负责人关系。Atlas 的已知责任人仍是赵启，北极星只是其事件消费者之一；若出现新的消费者，也需由明确文档记录后才能形成新关系。

这一边界也能用于检验系统是否会把事件消费者、服务负责人和同部门人员错误合并为同一责任主体。

若资料没有明确记录新的负责人或依赖方向，系统应保持未知，不以常见架构经验补全。
