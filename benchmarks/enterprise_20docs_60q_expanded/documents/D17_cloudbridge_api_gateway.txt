云桥 API 网关用于集团统一 HTTP 接入、路由治理和部分流量控制，是多个上层应用暴露接口时使用的共享服务。网关把外部请求按照规则转发到相应后端，并对接入路径进行统一管理。它解决的是网络接入和路由问题，不负责知识检索、用户权限策略或 Kafka 事件分发，因此在系统关系分析中需要与其他共享服务区分。

魏衡负责云桥 API 网关。魏衡是应用架构部的平台架构师，主要关注 API 网关、服务接入规范和共享平台架构。云桥由魏衡负责，与赵启负责 Atlas 的事实可以共同说明两个共享服务负责人来自同一个应用架构部，但并不意味着两项服务由同一个人负责。人员、部门和服务责任需要分别建模。

云桥使用 Kong 作为核心网关组件，并使用 Redis 保存部分限流状态。Kong 负责请求路由和网关策略执行，Redis 用于保存部分需要快速访问的运行状态。Redis 也出现在猎户座和星图等系统中，但共享技术并不表示这些系统互相依赖。知识库不能仅根据“都使用 Redis”建立业务关系。

云桥为曙光客户门户和天枢知识平台的外部接口提供路由能力。对于这两个项目，ROUTES_FOR 表示网关为其流量提供接入与路由，不表示云桥负责门户或天枢的业务逻辑。曙光仍由苏澄负责，天枢仍由林岚和赵启共同负责。路由关系同样不能替代项目内部的调用和依赖关系。

云桥不承担 Kafka 事件分发职责；事件分发由 Atlas 事件服务负责。虽然云桥和 Atlas 都属于应用架构领域的共享服务，但云桥处理 HTTP 请求，Atlas 处理消息事件。若问题要求比较两者职责，应明确回答不是同一种职责。本文件也不把 Kafka 描述成云桥的核心组件，避免把同部门的技术栈错误合并。

云桥文档适合验证共享技术与业务关系的区别。Redis 在多个系统中复用，但技术复用不能建立项目依赖；Kong 只说明网关实现，Kafka 则属于 Atlas 的事件链路。回答职责问题时应优先依据明确谓词，而不是依据组件名称相似度。

网关文档中的路由对象数量可能持续增长，但新增路由只说明接入范围扩大，不代表云桥接管上层项目。服务治理中应持续保持 ROUTES_FOR、USES 和 RESPONSIBLE_FOR 等关系的边界，避免把网关作为所有业务系统的直接负责人或事件中心。

对于新增路由对象，同样只记录路由关系，不自动扩展负责人或业务依赖。
